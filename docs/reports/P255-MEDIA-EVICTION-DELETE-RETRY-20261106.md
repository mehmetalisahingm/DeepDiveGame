# #273 / #269 follow-up — medya tahliye silme hatasında güvenli yeniden deneme

#273, kanal dolduğunda tahliye edilen klibin dosyasını **yalnız onu artık listelemeyen kampanya kaydı başarılı olduktan sonra** silmek üzere `PendingMediaDeletes` ekledi. Bu sıralama doğru. Ancak `RecordingMediaCaptureBinding.DeleteClipFile`, eski genel amaçlı `DeleteQuietly` metodunu kullanıyordu: `IOException` ve `UnauthorizedAccessException` hataları sessizce yutuluyordu. Böylece kuyruk `Flush`, silme işlemini başarılı sanıp ID'yi listeden çıkarabiliyor ve disk dolmasına yol açan medya artıkları bırakabiliyordu.

Bu düzeltme yalnız tahliye edilmiş, başarılı save sonrası silinecek dosyada `File.Delete` hatalarını dışarı aktarır; `PendingMediaDeletes.Flush` mevcut tasarımıyla başarısız ID'yi listede tutup sonraki **başarılı** save'de tekrar dener. Kayıt reddinde geçici dosyayı temizleyen `DeleteQuietly` davranışı bilerek değiştirilmedi. Olmayan dosyayı tekrar silmek .NET `File.Delete` için idempotenttir. Geçersiz klip ID'si dosyaya erişmeksizin hata üretir ve kuyrukta kalır.

`P255ClipFileDeletionRetryTests`, başarısız yolun kuyrukta kalmasını ve geçerli test medyasının save öncesinde yerinde/flush sonrasında silinmesini sınar. Mevcut `ChannelHistoryTests` başarısız save ve silme kuyruğu senaryolarını kapsar. **Sınır:** queue hâlen süreç belleğinde; başarılı save ile deletion arasında süreç ölürse yeniden başlatmada artık dosyanın disk temizliği için kalıcı ek tarama gerekebilir. Bu ayrı bir disk kotası/kurtarma görevidir. Windows GPU, gerçek dolu disk veya host çökmesi bu PR ile çalıştırılmadı.
